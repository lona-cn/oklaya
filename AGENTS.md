# Agent guidance

These instructions apply to the entire repository. Start with `README.md` (or `README.zh-CN.md`), then read the contract relevant to your change. Keep changes within the requested scope; do not treat historical examples as new feature requirements.

## Workspace boundaries

- `laya-inference`: model download and integrity checks, tokenizer, ONNX session, typed questions/results. The public Rust types and JSON representation live here. Keep inference independent of HTTP and browser code.
- `laya-cli-server`: the `laya` and `laya-inspect` executables. `laya serve` owns the loaded inference engine, exposes the versioned JSON API, and keeps bounded in-memory metadata-only request statistics/history.
- `laya-gui-server`: a separate Tauri 2 administrator app with its own loopback dashboard. It starts/stops **only** its own CLI inference subprocess and displays health/metrics/history; it does not serve the decision workspace or perform inference.
- `laya-gui-client`: a Tauri 2 decision-workspace app that also serves its interactive page to ordinary browsers. It owns the HTML/CSS/JS and same-origin prediction proxy; it does not load the model. Both GUI apps open windows by default and accept `--no-window` for browser-only mode.

Follow existing request/result types rather than defining a second decision schema. For HTTP changes, keep `docs/http-api.md` and `docs/openapi.yaml` consistent with the implementation. The servers bind to loopback by default and have no authentication; do not suggest exposing them publicly without access controls. Keep JSON errors as non-2xx HTTP responses without leaking internal paths or stack traces.

## Development and checks

Run commands from the workspace root:

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo build --workspace --release
```

The normal workspace tests do not require downloading a model. Model-backed reference tests require `LAYA_RUN_MODEL_TESTS=1 cargo test -p laya-inference --test reference` (on Windows, set the environment variable using the active shell's syntax). `LAYA_MODEL_DIR` can point to an existing model folder. These tests compare the multilingual graph and tokenizer with recorded official Python ONNXAgent outputs; do not replace their fixtures with results generated by the Rust implementation under test. Python is not required at runtime.

For behavior changes, also exercise the affected executable or HTTP/browser flow with a real request; unit tests alone do not prove desktop and browser flows. Build the CLI binary alongside the administrator: it resolves a sibling `laya[.exe]` by default unless `--laya-bin` is supplied. The administrator cannot stop an unrelated inference process. Keep request history metadata-only (no state, question text or criteria), capped at 100 in memory, and document the paging contract. Preserve the CLI convention: prediction JSON on stdout, diagnostics on stderr. Keep model artifacts, CUDA DLLs, benchmark scratch data, and build outputs out of commits; `models/`, `gpu-runtime/`, and `target/` are ignored.

## Documentation

`README.md` is the default English entry point; `README.zh-CN.md` is its Chinese counterpart. Update both when changing user-facing commands or capabilities, and preserve their language-switch links. Model provenance and limitations belong in `docs/model-source.md`; prompt and decision semantics in `docs/inference-contract.md`; CUDA setup in `docs/windows-cuda.md`. Do not add one-off test or implementation reports to the repository.
